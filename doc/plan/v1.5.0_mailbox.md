# HARDWARIO STICKER — NFC command channel over the ST25DV FTM mailbox (mailbox-only)

Plan for the PR that moves every interactive NFC command (`GetInfo` / `GetConfig` /
`SetParam` / vendor operations / claiming) from NDEF EEPROM records to the ST25DV
**Fast Transfer Mode (FTM) mailbox**, so that a phone completes the whole exchange in
**one tap with the phone held still** — on iOS exactly as on Android. Resolves
[#313](https://github.com/hardwario/sticker-firmware/issues/313).

> Requested 2026-09-09: "make a plan for moving NFC from NDEF to the mailbox: effort,
> Android/iOS feasibility, what we gain and lose, possible problems". Design decisions D1–D8
> below were taken in the same discussion; D8–D11 are implemented by the claiming PR.

**Status:** plan for [PR #414](https://github.com/hardwario/sticker-firmware/pull/414)
(`feat(nfc): using mailbox`, draft, into `v1.5.0`); the implementation commits follow (§8).
**Depends on the claiming / `plain_text` PR [#415](https://github.com/hardwario/sticker-firmware/pull/415)** (`doc/plan/v1.5.0_claiming.md`): mailbox channel
0x03 only forwards to the `APP_CMD_TRANSPORT_PLAIN_TEXT` transport that PR introduces, and the
removal of the `clm` NDEF record (D8) needs its `get_claim_info` command. Every hardware claim is
backed by the ST25DV datasheet (DS10925 rev 9), the firmware git history, or a cited
measurement; items that can only be settled on hardware are listed as bench experiments (§6).

---

## 1. Context

**Problem.** Interactive NFC commands are unreliable on iOS. The cause is not app code:

- The ST25DV user EEPROM is single-port. Firmware writes the response record (`hio.stck:rsp`)
  and the info record **only while the RF field is off** — `nfc_wait_field_off()`
  (`app_nfc.c:989`) waits up to 1800 ms for `EH_CTRL_Dyn.FIELD_ON=0`, else `-EBUSY`. The gate
  exists because an EEPROM I2C transfer under RF contention wedged i2c1 → the sensor sweep held
  `g_app_sensor_data_lock` → `app_alarm_poll()` (`app_alarm.c:1024`) blocked the main loop →
  no `app_wdog_feed()` (`main.c:579`, 10 s window) → SoC reset (`e33537b`, `e8dc177`).
- Android reader mode can drop the field silently (the app ends the session between write and
  read). **iOS Core NFC cannot** — the only field-off window is the operator physically
  lifting the phone. Today's iOS flow (`_runExchangeIos`,
  `sticker_nfc_transceiver.dart:805–1070`): tap → write → "lift for ~2 s" → tap → read.
  **Two taps per command, 2 × page count for `GetConfig`**, each page its own session.

**Solution.** The ST25DV 256 B **mailbox** is dual-port RAM served by RF and I2C **with the
field on**, with a hardware handshake (`RF_PUT_MSG` / `HOST_PUT_MSG`). No field-off window →
one tap, phone held still, iOS == Android.

**History.** The mailbox existed in firmware: PR #148 (2026-06-18) → encrypted in #194 →
removed in #239 (2026-07-01) as collateral of dropping NFC DFU. The Manager-App still carries
an Android mailbox transport (`lib/features/sticker/nfc/sticker_nfc_iso.dart`, debug console
only); an iOS variant was never written — the June decision "iOS can't do FTM" was a judgement
call, never measured.

## 2. Decisions (2026-09-09)

| # | Decision | Consequence |
|---|---|---|
| D1 | **RF-initiated FTM**: the phone enables the mailbox itself (custom command 0xAE); firmware never reads EEPROM under a held field. The original #313 proposal (`enter_mailbox` over NDEF) is rejected — it required an EEPROM read under the held field, exactly what the `e33537b` gate forbids. | No protobuf change; proto ids 19/20/22 stay `reserved`. |
| D2 | **Mailbox-only firmware, no backward compatibility.** The interactive NDEF channel (`hio.stck:cmd`/`vnd` → `rsp` → `ack`) is removed entirely. | Firmware v1.5.0 is breaking for the Manager-App; lockstep release. |
| D3 | **Battery-less configuration (boot-staged `cmd`, #147/#250) is dropped.** | Boxed units cannot be pre-configured without a battery. |
| D4 | **Legacy firmware 1.4.0** is supported only by the Manager-App on **Android**: auto-detected by the probe (0xAE → 0xAD read-back `MB_EN=0` = legacy) plus a manual "Sticker 1.4.0" override. The iOS lift choreography is deleted from the app. | The 1.4.0 fleet stays on 1.4.0 forever (no NFC DFU) → the Android legacy mode is permanent. |
| D5 | **Vendor channel (`vendor_token`) over the mailbox** with a 1-byte channel prefix. | Firmware picks the key from the prefix; the app codec is unchanged. |
| D6 | **`inf` record back to the external type `hio.stck:inf`, no MIME.** Tap-to-launch (#298) is dropped; the user opens the app. | Android intent filters go away (the source of the RF regression apps/manager#910). Any generic reader still shows the serial in the payload. |
| D7 | **`MB_MODE` cannot be set = hardware / production defect → production-tester gate.** No fallback in firmware or app. | `device_status` bit 13 + `ats device info` line; the tester rejects the unit. |
| D8 | **Claiming only into a powered device, over the mailbox.** The `hio.stck:clm` NDEF record is removed; `ClaimInfo` is served by the plaintext command `get_claim_info` on mailbox channel 0x03 while the claim window is `active`. | Battery-less claiming is no longer possible — changes the requirement from the July e-mail (`claiming_process.md` §1); must be communicated. Security gain: `claim_token` can no longer be read off an unpowered box. |
| D9–D11 | **Claiming redesign lives in its own PR** — transport `plain_text` (generic plaintext command allowlist, first user `get_claim_info`, later `get_basic_info`), explicit two-state claim window `active`/`done` with no automation, rename `clm_ack`/`clm_rearm` → `claim_done`/`claim_active`. See PR #415 / `doc/plan/v1.5.0_claiming.md`. | #414 consumes it: channel 0x03 → `app_cmd_handle(APP_CMD_TRANSPORT_PLAIN_TEXT, …)`; `clm` record and its automation are already gone or reduced when #414 lands. |

## 3. Verified facts

### 3.1 ST25DV datasheet (DS10925 rev 9)

| Fact | Consequence |
|---|---|
| `MB_MODE` (static 0x000D, E1 = 0x57) is writable only inside an I2C security session (the chip's **internal I2C password**, 8 B, factory all-zero). EEPROM-persistent; it only **authorises** FTM. | Set **once** in the existing boot path `nfc_enable_rf_write_it()` (`app_nfc.c:865`, which already writes GPO with that password today). Never cleared. The phone presents no password — RF access to the mailbox is password-free; authentication is AES-CCM. |
| `MB_CTRL_Dyn` (0x2006, E0 = 0x53) bit0 `MB_EN` is **"R always, W always" from both RF and I2C, no password** (RF: Write Dynamic Configuration 0xAE @0x0D). bit1 `HOST_PUT_MSG`, bit2 `RF_PUT_MSG`. | The phone enables FTM itself (D1). |
| `MB_EN` auto-clears only when `MB_MODE=0` or VCC is lost. Dynamic registers are volatile but kept while **either the RF field or VCC** is present. | A "stuck FTM" survives an MCU reset and LPD-high while a phone sits on the tag → firmware clears `MB_EN` explicitly (R2). Without a field, LPD-high wipes them (`IT_STS_Dyn` reads 0x00 every pass, `app_nfc.c:2232`). |
| **Caution §5.1.2:** every EEPROM write (user or system) transits the FTM buffer → with `MB_EN=1` an I2C EEPROM write is **NACKed** and an RF write returns **error 0Fh**. Reads are not restricted. | Explains the "truncated NDEF" of `0a5b7f6` and the revert `1c365c8`: firmware could not **update** the info record (a stale, shorter record remained). The boot `mb_disable` NACKed because the static write ran with `MB_EN=1`. |
| RF Write Message (0xAA) only when the mailbox is free (`HOST_PUT_MSG=0 && RF_PUT_MSG=0`). I2C read of the last byte + STOP clears `RF_PUT_MSG`; RF read of the last byte clears `HOST_PUT_MSG`. | Hardware flow control (ping-pong). |
| I2C mailbox write must start at 0x2008 in one transaction (≤ 258 B); `HOST_PUT_MSG` set at STOP. `MB_LEN_Dyn` (0x2007) = length − 1. | `mb_write_msg()` = one `i2c_write` + retry. |
| `MB_WDG` (0x000E): 2^(n−1) × 30 ms, 0 = infinite. | Leave 0. |
| GPO static (0x0000, E1, password): bit4 `RF_PUT_MSG_EN`. Today `ST25DV_GPO_WANT = 0xC8`. | → `0xD8`: a GPO pulse on every phone write wakes the poll thread; polling is the fallback. |
| Arbitration "first talk first served": I2C is NACKed **only during an RF transaction**, not for the whole field presence. | 1-byte dynamic-register reads under a held field are safe (firmware does them today). |
| The mailbox needs VCC (LPD low): "presence of a DC supply is mandatory to get RF access to the mailbox". `EH_CTRL_Dyn` has a `VCC_ON` bit. | Without a battery there is no mailbox → the app detects it via 0xAD. LPD stays low for the whole session. |
| RF commands: 0xAA Write Message, 0xAB Read Message Length, 0xAC Read Message (`pointer`, `count−1`), 0xAD/0xAE Read/Write Dynamic Configuration. IC Mfg code 0x02. **These are ST's standard commands in the ISO 15693 "custom" range (0xA0–0xDF), identical on Android and iOS.** | Android `NfcV.transceive` (exists), iOS `Iso15693.customCommand` (to be written). |

### 3.2 iOS Core NFC

- `Iso15693.customCommand` works only in **non-addressed** mode (flags `highDataRate` = 0x02);
  Core NFC inserts the IC manufacturer code itself, takes the command code as an `Int`,
  **strips the response-flags byte** and surfaces a tag error as an exception (ST community
  threads; verified in the `nfc_manager 4.2.1` Swift/Pigeon sources).
- ST's own iOS apps — **ST25 NFC Tap** (FTM demo, "Send Custom Command") and **ST25DV-I2C
  CryptoDemo** — drive FTM through Core NFC.
- The Manager-App already uses `NFCTagReaderSession`; the same `NfcTag` yields `NdefIos` and
  `Iso15693Ios` → NDEF read of `inf` plus the custom-command loop **in one session, one tap**.
  The `TAG` entitlement is already declared.
- Limits: session 60 s; **tag connection 20 s (hard limit, Apple engineer)**; reading 256 B
  in one 0xAC occasionally fails with `NFCError 102` → read in ≤ ~200 B chunks.

### 3.3 Android

- 0xAA/0xAB/0xAC over `NfcV.transceive` were HW-verified on 2026-06-17 (GetInfo round trip in
  one session; paged config ~15 s vs ~30 s over NDEF). `sticker_nfc_iso.dart` still compiles.
- The phone never used 0xAD/0xAE — to be added. Presence check ~130–250 ms.
  `getMaxTransceiveLength()` ~253 B → Write Message payload ≤ ~249 B. Discovery needs
  `{iso15693, iso14443}` together.

Restorable: `mb_enable()`, `mb_write()`, `mb_wait_host_put_cleared()`,
`app_nfc_serve_mailbox()` (commit `73b2060`, +195 lines), the `nfc mailbox` shell, test plan

| # | Bug in the old code | Fix |
|---|---|---|

### 3.6 The claim window today (correction to `claiming_process.md` §3 step 4)

Deleting `clm` over RF **no longer closes the window** — the unauthenticated trigger was
removed in #360 (`1f16497`); firmware re-lays `clm` on the next poll. The only live

inside `handle_encrypted_cmd()` (`:1487`). Both need a powered unit and an authenticated
command → D8/D10 match how the window actually behaves, minus the implicit trigger.

## 4. Design

### 4.1 Phone ↔ firmware protocol (one tap)

```
phone                                                firmware (poll thread, app_nfc.c)
─────────────────────────────────────────────         ──────────────────────────────────────────
connect (NFCTagReaderSession / reader mode)
read NDEF: hio.stck:inf (serial:cfgver:nonce)  ──►    GPO FIELD_CHANGE↑ → wake → nfc_access_begin
0xAD EH_CTRL_Dyn → VCC_ON?                            (LPD low, held while FIELD_ON)
  VCC_ON=0 → "insert a battery" (no claim either)
0xAE MB_CTRL_Dyn=0x01 ; 0xAD read-back ≤1 s    ──►    MB_EN=1 → mb_serve_locked()
  MB_EN=0 → legacy 1.4.0 (Android NDEF / iOS N/A)
[claim] 0xAA [0x03][Command{get_claim_info}]   ──►    chan 0x03 → app_cmd_handle(PLAIN_TEXT)
        poll 0xAD, 0xAB/0xAC             ◄──          [0x03][0x01][Response{claim_info}] if active,
        → ATELOS → secret_key/vendor_token            Error NOT_READY "claimed" if done
0xAA [0x01][enc Command{claim_done}]           ──►    window → done (explicit, same session)
0xAA Write Message([0x01][enc Command]) ≤240 B ──►    GPO RF_PUT_MSG pulse / poll 20 ms
                                                      RF_PUT → MB_LEN → mb_read_msg → chan → key
                                                      handle_encrypted_cmd() (anti-replay, cache;
                                                      no implicit claim close, D10)
poll 0xAD until HOST_PUT_MSG (≤1 s)        ◄──        mb_write_msg([chan][enc Response])
0xAB len ; 0xAC read (≤200 B chunks)                  mb_wait_host_put_cleared(1 s)
… further commands (GetConfig pages, SetParam) …
0xAE MB_EN=0 / lift the phone                  ──►    FIELD_ON=0 | idle 3 s | max 30 s | MB_EN=0
                                                      → mb_set_en(false) → nfc_access_end
                                                      → deferred action (save/reboot) → inf refresh
```

**Mailbox frame:** `[chan 1 B][payload]`.

| chan | Direction / payload | Key | cache | `clm_consume` |
|---|---|---|---|---|
| `0x01` cmd | `[serial BE32][nonce BE32][AES-CCM ct + 16 B tag]`, byte-identical to today's `hio.stck:cmd`/`rsp` payload (request without version byte, response `0x01 \|\| Response`) | `secret_key`, `APP_CMD_TRANSPORT_NFC` | on | yes |
| `0x02` vnd | same | `vendor_token`, `APP_CMD_TRANSPORT_VENDOR` | off | no |
| `0x03` plain | request `[0x03][Command protobuf]` (no version byte), response `[0x03][0x01 \|\| Response protobuf]` — transport `APP_CMD_TRANSPORT_PLAIN_TEXT`; only commands declaring `plain_text` are dispatched (`get_claim_info`), anything else → `NOT_READY "transport not allowed"` | none | off | no |
| other / `0x00` | rejected, no reply (also guards against zero-filled RAM after POR) | — | — | — |

Plaintext ≤ 256 − 1 − 8 − 16 = **231 B**. `DUMP_PAGE_BUDGET_NFC` 450 → **200** (a constant;
the NFC transport is the mailbox only, no dual budget).

**Security.** Entry (0xAE) is unauthenticated — as is writing a `cmd` record into EEPROM
today. Channels 0x01/0x02 go through `handle_encrypted_cmd()` (`app_nfc.c:1433`): AES-CCM,
serial check, monotonic nonce with a 1024 window persisted before execution, byte-exact
response cache; a rejected frame gets no reply. Channel 0x03 is a configen-gated allowlist (D9): the only command it can reach today is
`get_claim_info`, which discloses what lies in plaintext in the `clm` record today, but **only
on a powered unit while the claim window is `active`** —
a shelf attacker cannot read `claim_token` off an unpowered box (narrows the front-running
window of `claiming_process.md` §4). Holding `MB_EN=1` blocks EEPROM writes only while the
attacker also holds the field; firmware clears `MB_EN` on field-off / idle / boot.

### 4.2 Session state machine (`mb_serve_locked()`, caller holds `m_lock`, LPD low)

```
enter:  nfc_keep_awake(); nfc_led_detected(); t0=t_last=now; err_budget=8
loop:   now−t0 > 30 s → EXIT(max) ; now−t_last > 3 s → EXIT(idle)
        mb_read_ctrl(): error → --err_budget==0 → EXIT(i2c)
        !(ctrl & MB_EN) → EXIT(phone cleared)
        FIELD_ON==0 three times in a row (~60 ms) → EXIT(field)
        !(ctrl & RF_PUT_MSG) → k_sem_take(&m_gpo_sem, 20 ms); keep_awake every ≤1 s; continue
        mb_read_len(); mb_read_msg(m_buf,len)          /* reading the last byte clears RF_PUT */
        chan=m_buf[0]:
          0x03 → app_cmd_handle(PLAIN_TEXT, m_buf+1, len−1, m_resp_buf+1, 255) (no decrypt, no cache,
                 no claim side effects); m_resp_buf[0]=0x03; mb_write_msg; wait HOST_PUT; continue
          0x01/0x02 → key/tp/cache per table ; else → led_rejected; continue
        nfc_led_processing(); t_last=now
        handle_encrypted_cmd(key, tp, cache, m_buf+1, len−1, m_resp_buf+1, 255, …)
        ret≠0 → nfc_led_rejected(); continue           /* no reply */
        m_resp_len → m_resp_buf[0]=chan; mb_write_msg(); mb_wait_host_put_cleared(1 s, also on field-off)
        !replayed && action≠NONE → m_cmd_action=action → EXIT(action)
EXIT:   mb_set_en(false) (retry, best effort); nfc_led_off()
        FIELD_ON==0 → immediate inf reconciliation (nonce advanced → rewrite stale inf)
        m_cmd_action≠NONE → nfc_run_deferred_cmd_actions() after return (the m_cmd_action_ready
        gate goes: the reply is in MB RAM instantly, waiting for HOST_PUT clear replaces the #242 ack gate)
```

Integration into the poll thread (`nfc_poll_thread_fn`, `main.c:229`; wake only on GPO
`m_gpo_sem`):

- `app_nfc_poll()` (`app_nfc.c:2235`) gets its own body: under `nfc_access_begin()` first
  read `MB_CTRL_Dyn`: `MB_EN=1 && FIELD_ON` → serve; `MB_EN=1 && !FIELD_ON` → **stuck guard**
  `mb_set_en(false)` + WRN; then the `inf` reconciliation (simplified `nfc_check_locked`).
- **Field-present mode (R20):** while `FIELD_ON=1` the thread does not sleep and does not
  raise LPD — it polls `MB_CTRL_Dyn`/`FIELD_ON` every ~50 ms (GPO semaphore as an alarm)
  until the field drops, bounded to 30 s. Today firmware waits 1.8 s under the field and then
  sleeps with LPD high; a phone that sends 0xAE later (iOS sheet) would hit a low-power chip.
- `nfc_wait_field_off()` (`:989`) stays for the `inf` EEPROM writes; each iteration also reads
  `MB_CTRL_Dyn` and returns `false` + `m_mb_requested` when `MB_EN=1`.
- PM: `nfc_keep_awake()` (`:388`, 5 s window) re-armed every ≤ 1 s → Stop2 never lands inside
  a session (#329). IWDG: fed from the main loop (`main.c:579`); the only coupling is i2c1
  contention → short transfers + error budget.
- Deferred actions come from the mailbox only: after `HOST_PUT` clears (or a 1 s timeout) →
  `m_cmd_action` → `app_nfc_take_cmd_action()` → `nfc_run_deferred_cmd_actions()`
  (`main.c:129`, unchanged) after teardown. A reboot ends the session; the app re-probes.
- `inf` refresh: the nonce advanced → right after field-off in the same poll pass the
  `m_seen_inf` mismatch rewrites it (existing branch `app_nfc.c:2138–2171`, which becomes the
  main post-command path). The implicit `clm_consume()` call inside `handle_encrypted_cmd()`
  (`:1487`) is removed (D10); the window closes only on `claim_done`.

### 4.3 Boot (`nfc_enable_rf_write_it()`, `app_nfc.c:865` — extension)

1. Read `MB_CTRL_Dyn`; if `MB_EN=1` → `mb_set_en(false)` **before any EEPROM write** (Caution).
2. `nfc_present_password()` (`:827`, the chip's default all-zero I2C password) + 15 ms as today.
3. GPO static `0xC8 → 0xD8` (read-modify-write only if different + verify, `:887–904`).
4. `MB_MODE` read-modify-write only if different, `TW + 5 ms`, read back. On failure →
   `m_mb_available=false`, `LOG_WRN`, return 0 (GPO/init continue).
5. `GPO_CTRL_Dyn` as today.

`app_nfc_mailbox_available()` → **`APP_DEVICE_STATUS_MAILBOX_DOWN = 1u << 13` (0x2000)** in
`Info.device_status` (next free bit; bits 6–7 are reserved for alarm categories;
`app_cmd.h:35–54`, `app_cmd.c:156–179`, `print_device_status()` `app_ats.c:1164–1176`) plus a
`Mailbox: available|unavailable` line in `ats device info` after `app_ats.c:1228`. **D7: the
production tester rejects a unit with bit 13 set.** The bit also reaches the backend for free
through `GetInfo`.

### 4.5 Claiming (D8; detail in PR #415, `doc/plan/v1.5.0_claiming.md`)

What #414 contributes: channel 0x03 forwards `[Command]` to

rename, NVS migration and the tester/ATELOS flow — is the claiming PR. Resulting app flow:
tap → `inf` → probe → `get_claim_info` (0x03) → ATELOS → keys → `claim_done` (0x01) in the same
session. Without a battery the app shows "insert a battery" (`VCC_ON=0`).

## 5. What we gain / what we lose

**Gain**

- **iOS parity** (acceptance criteria of #313): `GetInfo`, multi-page `GetConfig` and
  `SetParam` in one tap with the phone held still.
- **Speed on Android too:** ~3–4 s per command → ~0.1–0.3 s per exchange; a whole
  configuration and the claim in one session.
- **One interactive state machine in firmware** (no `rsp`/`ack`/retry across field-off
  windows, none of the #164/#242/#340-M3 specialities), one NDEF record, one transport in the
  app, deterministic UX.
- **The tag stays clean:** only `inf`; `cmd`/`rsp`/`clm` are never written → zero EEPROM
  wear, hardware flow control, neither `claim_token` nor a response ever sits on the tag.
- **The claim window closes explicitly** with `claim_done` in the claim session, not at some later
  tap; the latch shrinks to two states with no automation.
- **No protobuf/codec change**; net flash **negative** (estimate −0.5…−1 KB text:
  `nfc_write_response` 168 B, `app_nfc_restore_info` 84 B, ~230 B of `parser_callback`,
  ~350 B of the `app_nfc_check` blob, the clm arm/commit/revert + `build_claim_payload` leave;
  `mb_serve_locked` ~500 B arrives; LTO figures are directional). RAM: six flags and the clm
  tag state go; `m_resp_buf`/`m_resp_cache_*` (1536 B) stay.

**Lose / consequences**

- **Battery-less configuration** (#147/#250) and **battery-less claiming** (D3/D8):
  pre-configuring or claiming boxed units in a warehouse is gone; the customer requirement
  changes.
- **Breaking for the Manager-App:** firmware 1.5.0 needs the mailbox-capable app; 1.4.0 units
  work only through the permanent Android legacy mode (no NFC DFU). An iOS user with a 1.4.0
  unit has no interactive configuration.
- **Tap-to-launch** (#298) goes away; the user opens the app.
- Plaintext responses ≤ 231 B → `GetConfig`/history in more pages; `GetInfo` ≈ 80–90 B
  without alarms, the existing trim loop (`app_cmd.c:1387`) drops alarms beyond ~17 active.
- iOS session ≤ 20 s; the Web NFC bridge tool loses interactive commands (dev tool); HIL
  scripts and `sticker_nfc_frame.py` move to prefixed mailbox frames.
- **The phone-free hardware test of commands is gone** (firmware cannot set `RF_PUT`).
  Replacement: `tests/nfc_hw` emulator + `nfc-proxy-app`.
- A session holds `m_lock`/LPD low for ≤ 30 s; ~1–2 mA for the duration — negligible.

## 6. Risks and mitigations

| # | Risk | Mitigation | Bench experiment |
|---|---|---|---|
| R1 | I2C NACK on collision with an RF transaction / presence check. | 20 × 2 ms retry; 1 B register < 0.2 ms; 256 B RAM @ 100 kHz ≈ 25 ms in 64 B chunks; error budget 8. | 1000 exchanges with the phone on the tag, 0 errors. |
| R2 | **Stuck `MB_EN`** → EEPROM writes NACK (`inf` restore). | Teardown `MB_EN=0`; poll guard; boot clear before static writes; `write_mem` NACK → clear + retry; phone sends 0xAE 0x00 at the end. | `nfc mb on` → LPD high → 0xAD with and without field. |
| R3 | "Truncated NDEF" with `MB_EN=1` (`0a5b7f6`). | Per the datasheet a blocked **write**; the app reads `inf` **before** enabling; firmware clears. | `nfc mb on` → RF NDEF read (ST25 NFC Tap): full record? |
| R4 | `MB_MODE` cannot be set. | **D7: hardware/production defect → tester gate** (bit 13 + `ats device info`), no fallback. Low probability (the GPO write with the default password works on every bench unit today; the June NACK is explained by the Caution). | `MB_MODE` read-back after boot on bench units from several batches + 10 power cycles. |
| R5 | iOS 20 s connection limit. | Firmware idle 3 s / max 30 s; the app plans and continues in a new session. | GetConfig all pages + claim < 20 s. |
| R6 | iOS 0xAC 256 B read flaky. | App reads ≤ 200 B chunks. | iPhone models. |
| R7 | Android transceive ~253 B. | Request ≤ 249 B; app checks `getMaxTransceiveLength()`. | — |
| R8 | `Response.Info` > 231 B with many alarms. | Existing `-EMSGSIZE` trim + Error fallback (`app_cmd.c:1382–1403`). | — |
| R9 | Page budget 450 → 200 changes `page_count`. | The app honours `page_count`; ztest. | — |
| R10 | Debug RAM ~99 %. | Frames in `m_buf`/`m_resp_buf`; removing NDEF + clm frees RAM. | `.map` debug + release. |
| R11 | Race: FIELD↑ wakes firmware into `nfc_wait_field_off` before the phone sets `MB_EN`. | `MB_EN` check on every iteration; field-present mode; GPO `RF_PUT_MSG` pulse. | First-command latency < 300 ms. |

| R19 | Poll-thread stack 6144. | Session adds ~64 B of locals. | `kernel stacks` after a session. |
| R20 | ST25DV in low power (LPD high) when the phone arrives → 0xAE ineffective. | Field-present mode (LPD low while FIELD_ON); the app reads 0xAD after 0xAE and retries ~1 s. | 0xAE with LPD high under a field: does `MB_EN` set? Tap → `MB_EN=1` latency Android/iOS. |
| R21 | Probe on a unit without a battery. | `VCC_ON` before the probe → "insert a battery". | No battery: 0xAD VCC_ON=0, 0xAE → behaviour. |
| R22 | **1.4.0 fleet is legacy forever** (no NFC DFU). | Permanent Android legacy mode; auto probe + override; iOS 1.4.0 = no configuration. Find out how many 1.4.0 units shipped. | — |
| R23 | An old app / wrong override writes `cmd` into a 1.5 unit. | Firmware does not execute; debounce → `inf`; the app times out with a message. | ztest: cmd record on tag → no action, inf restored. |
| R24 | Channel prefix missing from `sticker_nfc_frame.py` / HIL scripts / manual test plan. | Update the tooling in the same PR (bench tooling outside the repo: `~/Documents/claude/Scripts/`). | — |
| R25 | The vendor channel has no rate limit; the mailbox ceiling is far above the field-off-gated NDEF. | Anti-replay + 128-bit key; optionally a 50 ms minimum between frames / max N rejections per session → `EXIT`. Low priority. | — |
| R26 | Loss of the phone-free hardware test of commands. | The `tests/nfc_hw` emulator models RF_PUT; `nfc-proxy-app` scripts as HIL; rewrite the playbook recipe. | — |
| R27 | The claim requirement change (battery-less → battery) is not agreed with the customer. | Communicate before the PR merges; rewrite `claiming_process.md` §1; the ATELOS API is unchanged (still `{SN, claim_token}`). | — |
| R28 | Without the implicit close (D10) an app that crashes between ATELOS confirmation and `claim_done` leaves `claim_token` readable on a powered unit. | Accepted: ATELOS refuses a second claim of the same SN (only the token leaks, not control); the app sends `claim_done` right after storing the keys; `ats claim done` as a manual fallback. | — |
| R29 | Channel 0x03 must never reach anything but the `plain_text` allowlist. | The allowlist is generated by configen in the claiming PR; a `tests/nfc_hw` case sends a non-allow-listed command on 0x03 and expects `NOT_READY`. | — |
